# 版本与兼容规则

**专业名称：** Spec Versioning  
**通俗解释：** 协议怎么升级，才不会让四个工具突然谁也读不懂谁。

## 1. 版本号

使用语义化版本 `MAJOR.MINOR.PATCH`，写入：

- 每个文档的适用版本；
- 每个事件的 `specVersion`；
- Schema 目录：`schemas/v{MAJOR}.{MINOR}/`（PATCH 不新开目录，除非修复 Schema 自身错误）。

当前：`0.1.0`（0.x 为预发布）。

## 2. 0.x 预发布

- 允许破坏性变更，但必须：更新 ADR 或变更说明、 bump MINOR 或 MAJOR、更新示例与测试。
- 产品集成 0.x 时应锁定次版本，并在 CI 校验 `specVersion`。

## 3. 兼容性承诺（目标：1.0+）

### 向后兼容（老消费者读新数据）

允许：

- 新增可选字段；
- 新增 `eventType` 值（老消费者忽略未知类型）；
- 新增 `resourceType` / `evidence.kind` 枚举值；
- 放宽可选约束。

不允许（须升 MAJOR）：

- 删除或重命名字段；
- 将可选改为必需；
- 改变字段语义；
- 改变 ID 算法致使既有 ID 失效且无映射；
- 改变时间格式（必须保持 RFC 3339 带时区）。

### 正向兼容（新消费者读老数据）

新消费者必须容忍缺失新增的可选字段。

## 4. Schema 文件策略

1. 规范性源：`schemas/v0.1/*.json`  
2. 破坏性变更：新目录 `schemas/v0.2/` 或 `v1.0/`，旧目录保留  
3. `$id` 必须包含版本路径  

## 5. 扩展

`extensions` 对象中的键建议使用反向域名：`com.example.foo`。  
扩展不得承载明文密钥。忽略未知扩展不得导致失败（除非产品显式开启严格模式）。

## 6. 弃用

弃用字段：文档标注 `deprecated`，至少保留一个 MINOR 周期；1.0 后删除须升 MAJOR。
